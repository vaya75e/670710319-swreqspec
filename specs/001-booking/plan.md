# Plan: จองคิวตรวจสุขภาพ (Booking)

## 1. สรุปแนวทาง
- ฟีเจอร์นี้ให้ผู้รับบริการที่ยืนยันตัวตนแล้วเลือกแพ็กเกจ วัน และช่วงเวลาตรวจสุขภาพ เพื่อดูช่วงว่างและยืนยันการจองได้ในหนึ่งกระบวนการ
- หน้าเลือกวัน/ช่วงเวลาและหน้าแสดงผลจะแสดงช่วงเวลาว่างพร้อมจำนวนที่นั่งคงเหลือ ตามแพ็กเกจที่เลือกและช่วงเวลาใน 30 วันข้างหน้า
- ระบบจะตรวจว่าผู้รับบริการมีคิวค้างในวันเดียวกันก่อนยืนยัน เพื่อปฏิเสธการจองซ้ำ และแสดงหมายเลขคิวเดิมถ้ามี
- เมื่อลงทะเบียนสำเร็จ ระบบจะใช้ transaction บันทึก booking ตัดที่นั่งคงเหลือ ออกหมายเลขคิว และส่งคำขอแจ้งเตือนแบบ asynchronous
- ระบบจะบันทึก audit log ทุกครั้งที่เข้าถึงข้อมูลการจอง และทำ retry ให้ข้อความแจ้งเตือนในกรณีส่งไม่สำเร็จ โดยไม่ให้การจองถูก rollback

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| MySQL | CON-TECH-01 | ใช้เก็บตาราง booking, slot, notification queue และ audit log |
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างหน้าจอเลือกแพ็กเกจ/วัน/ช่วงเวลาและแสดงผลยืนยัน |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้จัดการ API สำหรับค้นหาช่วงว่างและยืนยันการจอง |
| TLS 1.2+ สำหรับการรับส่งข้อมูล | NFR-SEC-01 | ใช้ในทุก API ที่ส่งข้อมูลผู้รับบริการและผลลัพธ์ booking |
| ระบบคิวส่งข้อความแบบ asynchronous | IF-NOT-01 | ใช้ worker สำหรับลง queue และ retry ข้อความ SMS/LINE |
| การอ้างอิง HN แทนเลขบัตรประชาชน | IF-HIS-01 | ใช้ในตาราง booking และ audit log เพื่อหลีกเลี่ยงการเก็บเลขบัตรประชาชน |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ FR |
|---|---|---|
| `patient_identity` | `patient_id`, `hn`, `verified_at`, `identity_source` | IF-IDP-01, FR-BKG-01, FR-BKG-02 |
| `package` | `package_id`, `name`, `description`, `status` | FR-BKG-01, FR-BKG-06 |
| `booking_slot` | `slot_date`, `slot_start`, `slot_end`, `package_id`, `quota`, `remaining_capacity`, `status` | FR-BKG-01, FR-BKG-03, FR-BKG-04, FR-BKG-06 |
| `booking` | `booking_id`, `hn`, `package_id`, `slot_date`, `slot_start`, `slot_end`, `queue_no`, `status`, `created_at`, `confirmed_at`, `message_status` | FR-BKG-02, FR-BKG-04, FR-BKG-05 |
| `notification_request` | `request_id`, `booking_id`, `channel`, `payload`, `status`, `retry_count`, `next_retry_at`, `last_error` | FR-BKG-05, IF-NOT-01, NFR-REL-02 |
| `audit_log` | `log_id`, `actor_user`, `access_time`, `hn`, `action`, `target_type`, `target_id` | DOM-PDPA-01 |

หมายเหตุ:
- ตาราง `booking` จะเก็บ `hn` จาก HIS เท่านั้น ตาม IF-HIS-01 และจะไม่เก็บเลขบัตรประชาชนในตารางการจอง
- ตาราง `booking_slot` จะคำนวณ `remaining_capacity` จากคิวที่ยืนยันสำเร็จและโควตารายช่วงเวลาที่กำหนดไว้
- ตาราง `audit_log` จะมีข้อมูลผู้เข้าถึง เวลา และ `hn` ตาม DOM-PDPA-01 อย่างน้อย 1 ปี

## 4. API / หน้าจอ

| ชื่อ | รายละเอียด | รองรับ FR |
|---|---|---|
| `GET /booking/slots` | คืนค่าช่วงเวลาใน 30 วันข้างหน้า พร้อมที่นั่งคงเหลือต่อช่วงเวลา โดยตัวกรองตามแพ็กเกจและวันที่ | FR-BKG-01, FR-BKG-06 |
| `GET /booking/availability` | ตรวจว่าช่วงเวลาที่เลือกยังมีที่นั่งว่างก่อนเปิดการยืนยัน หรือแสดง 3 ตัวเลือกแทนเมื่อเต็ม | FR-BKG-03, FR-BKG-04 |
| `GET /booking/duplicate-check` | ตรวจว่า HN เดียวกันมี booking ที่ยังไม่ได้ใช้ในวันเดียวกันหรือไม่ | FR-BKG-02 |
| `POST /booking/confirm` | รับแพ็กเกจ วัน และช่วงเวลา ส่งกลับ booking_id, queue_no และ status; หากเต็มให้ตอบกลับ 3 ตัวเลือกแทน | FR-BKG-03, FR-BKG-04 |
| `POST /booking/notification/retry` | ดึงข้อความที่ส่งไม่สำเร็จจาก queue และส่งซ้ำตามกรอบเวลา 5 นาที | FR-BKG-05, NFR-REL-02, IF-NOT-01 |
| หน้า `BookingSelectionPage` | แสดงแพ็กเกจ วัน และช่วงเวลา พร้อมจำนวนที่นั่งคงเหลือ และปุ่มยืนยัน | FR-BKG-01, FR-BKG-06 |
| หน้า `BookingConfirmationPage` | แสดงหมายเลขคิวและสถานะส่งข้อความยืนยันหลังยืนยันสำเร็จ | FR-BKG-04, FR-BKG-05 |

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| CON-TECH-01 | ใช้ MySQL สำหรับตาราง booking, booking_slot, notification_request และ audit_log | ใช้แล้ว |
| DOM-PDPA-01 | บันทึก audit_log ทุกครั้งที่เข้าถึงข้อมูลการจอง โดยมี actor_user, access_time, hn และ action | ใช้แล้ว |
| IF-IDP-01 | เพิ่มชั้นการตรวจสอบ precondition ใน API สำหรับทุกการเข้าถึง booking ว่า user ได้ยืนยันตัวตนแล้ว | ใช้แล้ว |
| IF-HIS-01 | ใช้ HN เป็นรหัสอ้างอิงใน booking และ audit log พร้อมไม่เก็บเลขบัตรประชาชนในตารางการจอง | ใช้แล้ว |
| IF-NOT-01 | ใช้ notification_request + async worker เพื่อส่ง SMS/LINE โดยไม่ให้ booking รอผลการส่งข้อความ | ใช้แล้ว |

## 7. ลำดับงาน

1. สร้าง schema MySQL สำหรับ booking, booking_slot และ audit_log ตาม FR-BKG-01, DOM-PDPA-01, IF-HIS-01
2. สร้าง API ค้นหาช่วงเวลาว่างใน 30 วันข้างหน้า พร้อมจำนวนที่นั่งคงเหลือ และการคำนวณใหม่เมื่อเปลี่ยนแพ็กเกจ ตาม FR-BKG-01, FR-BKG-06
3. สร้างตรวจสอบ duplicate booking สำหรับ HN ที่มีคิวค้างในวันเดียวกัน ตาม FR-BKG-02
4. สร้าง flow จองแบบ transaction: ตรวจความพร้อม -> จอง -> ตัดที่นั่ง -> ออกหมายเลขคิว ตาม FR-BKG-03, FR-BKG-04
5. สร้าง fallback เมื่อ slot เต็ม: ส่งข้อความ “ช่วงเวลาเต็ม” และแสดง 3 ตัวเลือกใกล้เคียง โดยไม่สร้าง booking ซ้อน ตาม FR-BKG-03
6. สร้าง worker ส่งข้อความยืนยันแบบ asynchronous และเก็บ queue retry ตาม FR-BKG-05, IF-NOT-01, NFR-REL-02
7. เพิ่ม audit log ในทุกการเข้าถึงข้อมูล booking และตรวจสอบ secure transport ตาม DOM-PDPA-01, NFR-SEC-01
8. ทดสอบครบตาม AC-BKG-01 ถึง AC-BKG-06 และปรับ performance ให้ตรง NFR-PERF-01

## 8. สิ่งที่ยังไม่ทำ
- สถานการณ์ “ยังไม่ได้ใช้” กำหนดว่าเป็นเฉพาะ HN เดียวกันหรือทุกคนในวันเดียวกัน? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- “ช่วงเวลาใกล้เคียง 3 ตัวเลือก” ควรคำนวณจากวันเดียวกันหรือข้ามวันได้บ้าง? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- “รหัสผู้รับบริการ” ใน audit log ต้องใช้ HN หรือใช้รหัสภายในระบบอีกแบบหนึ่ง? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- “ส่งข้อความไม่สำเร็จ” หมายถึงกรณีใด และ retry ต้องเริ่มภายในกี่นาที? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- โควตาที่นั่งต่อช่วงเวลาอ้างจากข้อมูลที่มีอยู่หรือถูกคำนวณจากการจองจริงโดยทันที? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- “ยืนยันภายใน 3 นาที” เริ่มนับเมื่อไรในกระบวนการจอง? ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
